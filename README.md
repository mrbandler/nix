# nix

Nix flake managing all of my machines, built on [den](https://den.denful.dev) and the
[dendritic pattern](https://dendrix.denful.dev/Dendritic.html): every `.nix` file under
`modules/` is auto-imported as a flake-parts module, so configuration is organized by
concern (aspects) instead of per-machine file trees. Hosts are one-line declarations;
den turns them into `darwinConfigurations` / `nixosConfigurations` automatically.

## Layout

```
modules/
├── dendritic.nix           # framework wiring (imports only)
├── inputs.nix              # shared flake inputs; aspect-owned inputs live in their aspect file
├── systems.nix             # extra systems beyond the hosts' (Linux, for CI)
├── fleet/                  # what every host and user gets
│   ├── defaults.nix        #   stateVersions, nix settings
│   ├── caches.nix          #   binary caches, for the machines and for anyone building the flake
│   └── schema.nix          #   typed host contract, fleet-wide includes (core)
├── tools/                  # working with the repo: building, linting, verifying
│   ├── nh.nix              #   per-host build apps (nix run .#<host>)
│   ├── treefmt.nix         #   formatters and linters (nix fmt, checks.treefmt)
│   ├── checks.nix          #   every host closure exposed as a flake check
│   └── update-report.nix   #   the update report posted on pull requests (packages.update-report)
├── hosts/
│   └── hermes.nix          # the Mac: host declaration and host aspect
├── users/mrbandler/        # user aspect: home-manager config + per-platform system config
└── aspects/                # one aspect per concern, folders mirror the old layout
    ├── core/               # on every host: tailscale, comin (opt-in)
    ├── apps/               # web, comms, knowledge, storage
    ├── desktop/            # keybinding contract, compositors, launchers, input
    ├── security/           # 1password
    └── theme/              # stylix, macOS appearance, wallpapers
```

`flake.nix` is generated by [flake-file](https://github.com/vic/flake-file); never edit
it by hand. Declare inputs in `modules/inputs.nix` (shared) or in the aspect that owns
them, then regenerate with `nix run .#write-flake`.

## Usage

Build a host closure without applying it (default action):

```console
nix run .#hermes
```

Apply the configuration:

```console
nix run .#hermes -- switch
```

Format and lint (nixfmt, statix, deadnix, actionlint via treefmt):

```console
nix fmt
```

Verify everything builds, host closures and lint included:

```console
nix flake check
```

## Updates

Inputs are updated through pull requests, never on a machine:

1. [`update.yml`](.github/workflows/update.yml) runs every Monday (or on demand from the
   Actions tab) and opens a pull request listing every input
   that moved, with auto-merge enabled.
2. [`ci.yml`](.github/workflows/ci.yml) lints first (nothing else runs if that fails),
   then discovers the hosts from the flake, builds each host closure on a runner of its
   architecture, pushes it to the Cachix cache and posts the **update report** on the PR
   (`nix run .#update-report`):
   - which inputs moved, with compare links
   - nixpkgs channel health: age of the pin, whether `nixpkgs-unstable` has moved on,
     links to [status.nixos.org](https://status.nixos.org) and the gating Hydra jobset
   - the closure diff (`nvd`): every package version that changes
   - Hydra build status (`nixpkgs/trunk`) of the changed packages. Hydra only builds
     free packages, so unfree ones always show "no Hydra job"
   - freshness of every app installed by the configuration (`environment.systemPackages`
     and `home.packages`): nixpkgs version vs upstream on Repology, and open nixpkgs
     bump PRs with [nixpkgs-tracker](https://nixpkgs-tracker.ocfox.me) links
3. The PR merges on its own once the `CI` check is green. Main therefore only ever
   contains configurations that built.
4. Each machine switches when it suits me. The closure CI built is in the cache, so a
   switch after an update is a download:

   ```console
   git pull && nix run .#hermes -- switch
   ```

   `nh` shows the package diff before activating.

### Pull-based switching with comin

[comin](https://github.com/nlewo/comin) polls this repository's `main` and switches the
machine to it automatically. It is wired up as the opt-in aspect `den.aspects.core.comin`
([`modules/aspects/core/comin.nix`](modules/aspects/core/comin.nix)) and enabled per
host by including it in the host aspect:

```nix
den.aspects.hermes.includes = [ den.aspects.core.comin ];
```
